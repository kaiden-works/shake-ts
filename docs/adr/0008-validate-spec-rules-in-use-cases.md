# 0008: 仕様が定める値の規則を Use Cases でバリデーションする

## ステータス

有効

## 背景

仕様は、完全性ハッシュのアルゴリズムが SHA-256、SHA-384、SHA-512 のいずれかであることなど、値の規則を定める。規則の対象の値は、提示された VC と、検証の途中で取得する文書に含まれる。[外部入力の形式のバリデーション](./0009-validate-input-format-in-controller.md)は本 ADR の対象外である。

[Clean Architecture を採用する](./0002-clean-architecture-layers.md)と決めた。仕様が定める値の規則を、どのレイヤーでバリデーションするかを決める必要がある。

## 選択肢

### 選択肢 A: entity の生成時にバリデーションする

entity を生成するときに規則を満たすかを確かめ、満たさなければ生成しない。

利点は、生成された entity が常に規則を満たすことである。

欠点は、仕様の改訂で規則が変わると、改訂前の規則で有効だった値から entity を生成できないことである。生成時のバリデーションは、その時点の規則で判定するためである。

### 選択肢 B: Use Cases でバリデーションする

entity はバリデーションを通った値だけを受け取り、usecase が規則を確かめる。

利点は次のとおり。

- バリデーションを、仕様の検証手順の一部として usecase に実装できる
- 改訂前の規則で有効だった値も扱える
    - 仕様は、検証者が対応するメジャーバージョンごとに検査を用意すると定めており、usecase をバージョンごとに用意すれば、値に合う規則でバリデーションできる
    - entity はバージョンによらず値を表すだけなので、改訂の影響を受けない
- [発行前チェックは verify の usecase を使う](./0003-shared-entities-and-per-feature-usecases.md)ため、同じバリデーションを共有できる

欠点は、entity の型だけでは、値が規則を満たすことを保証できないことである。

### 選択肢 C: Interface Adapters の controller でバリデーションする

controller が usecase を呼ぶ前に、入力の値が規則を満たすかを確かめる。

利点は、usecase がバリデーションを通った値だけを扱えることである。

欠点は、バリデーションする値の多くを controller が得られないことである。値の多くは usecase が取得した文書に含まれ、controller が入力を受け取る時点ではまだ取得されていない。

## 決定

選択肢 B を採用する。

選択肢 A は仕様の改訂後に過去の値を扱えず、選択肢 C はバリデーションする値の多くを得られない。選択肢 B だけが、取得した文書の値も含めて、仕様の検証手順のとおりにバリデーションできる。

### 選定に影響しなかった点

特になし。

## トレードオフ

entity を使う側は、値が Use Cases のバリデーションを通ったことを前提にする。この前提は型で表されない。
