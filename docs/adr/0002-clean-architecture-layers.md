# 0002: clean architecture のレイヤーで組む

## ステータス

有効

## 背景

[検証 CLI、発行前チェック CLI、発行 CLI、提示 CLI](../PRD.md#スコープ) の処理は 2 つに分かれる。1 つは仕様の規則である。もう 1 つは取得、署名検証、スキーマ検証、署名で、仕様が定めるものではなく、Node.js の API と外部ライブラリーで実現する。これを実装の詳細と呼ぶ。仕様の規則を実装の詳細から切り離すために、モジュール間の依存の向きを決める必要がある。

[テストはネットワークに接続しない](../PRD.md#制約前提)。各 CLI の処理は他の処理を呼び、その結果に応じて次の処理を決める。処理が実装の詳細をどの引数と順序で呼び、その結果をどう扱うかを、実装の詳細を実行せずに確かめる必要がある。

## 選択肢

### 選択肢 A: レイヤーを設けず、モジュールを平らに置く

モジュールごとに必要な依存を直接 import する。

利点は、ファイル数と間接層が少ないことである。

欠点は次のとおり。

- 仕様の規則が実装の詳細を直接 import するため、両者が同じモジュールに混ざる
- 呼び出す側のテストで実装の詳細を差し替えるには import 単位のモックが必要となる

### 選択肢 B: clean architecture のレイヤーで組む

entity、usecase、adapter の 3 つのレイヤーに分け、adapter は usecase に、usecase は entity に依存する。逆の依存は作らない。usecase は外部とのインターフェイスを port として定義し、adapter が実装する。usecase は port を引数で受け取る。他の usecase を呼ぶときは、その usecase も引数で受け取る。CLI の入口は `bin/` に置き、adapter の controller を呼ぶだけにする。

利点は次のとおり。

- 仕様の規則が entity と usecase に集まり、実装の詳細は adapter だけが持つ
- usecase のテストで、引数で受け取る port と usecase を関数に差し替えて、呼び出しの引数と順序、結果の扱いを確かめられる

欠点は、レイヤーごとにファイルと型が増えることである。

## 決定

選択肢 B を採用する。

仕様の規則を実装の詳細から切り離すには、両者を別のレイヤーに置き、依存の向きを固定する必要がある。選択肢 A にはその制約がない。あわせて、usecase の呼び出しと結果の扱いを確かめるには port を関数に差し替えられる構造が必要であり、選択肢 A では import 単位のモックが必要となる。

### 選定に影響しなかった点

特になし。

## トレードオフ

レイヤーごとにファイルと型が増える。
