# 0005: 例を URL のホスト名とパスのとおりに置く

## ステータス

有効

## 背景

[例は `examples/` に置く](./0004-examples-in-reference-implementation.md)と決めた。例の発行主体が URL で公開する文書は `*.example.shake.kaiden.works` の URL を持ち、検証 CLI はその URL から文書を取得する。

[テストはネットワークに接続せずに実行する](../PRD.md#制約前提)。テストでは、URL に対応する `examples/` のファイルを返して取得に代える。例を公開するときは、同じファイルを配信先の URL のパスに置く。どちらも URL とファイルの対応を必要とするため、URL で公開する文書の置き方を決める必要がある。

## 選択肢

### 選択肢 A: ユースケースごとに置き、URL との対応表を持つ

URL で公開する文書をユースケースごとのディレクトリーに置き、URL とファイルの対応表を別に持つ。

利点は、ユースケースごとに例をまとめて読めることである。

欠点は、文書を足すたびに対応表も直す必要があり、取得と配信の両方が対応表に依存することである。

### 選択肢 B: URL のホスト名とパスのとおりに置く

URL で公開する文書を `examples/published/<ホスト名>/<URL のパス>` に置く。ファイル名は URL のパスのとおりとし、拡張子を付けない。JWT VC Issuer Metadata は、仕様が定める `.well-known/jwt-vc-issuer/` 配下の URL のパスに置く。

利点は次のとおり。

- URL からファイルの位置が対応表なしで決まる
- 取得と配信が同じ規則で済む
- 仕様のリポジトリーの公開文書と同じく、URL と配信先のパスが揃う

欠点は、1 つのユースケースの例が発行主体ごとのディレクトリーに分かれることである。

## 決定

選択肢 B を採用する。

URL とファイルの対応は取得と配信の両方が使うため、対応表より規則で決める方が食い違わない。

### 選定に影響しなかった点

特になし。

## トレードオフ

- ユースケースごとのまとまりは `examples/README.md` の説明で補う
- ファイルに拡張子がないため、エディターが JSON と判定しない
- 配信先は、拡張子のないファイルに `Content-Type` を設定し、`.well-known` 配下を配信する必要がある
- あるパスをファイルにすると、その下のパスにファイルを置けない
